# Overview

The graphical user interface looks like a dark tactical command console: a near-black field, a single signal-orange accent, condensed uppercase headings, and monospaced figures, so that the Player reads the state of the agency at a glance, as an operator reads a heads-up display.

Every screen listed by the [Graphical User Interface](gui.md) is drawn with the same Design tokens and components, so every screen looks like part of one console. The rules here are the ones several screens share. How one screen arranges and sizes what it shows is not written down: its Screenshot shows it, in that screen's or panel's specification, e.g. [Main Menu](screens/main-menu.md).

# Screenshots

A Screenshot shows what a screen looks like in the game, so that a reader of a screen's specification sees the screen itself and the text does not have to describe it.

Every Screenshot is generated. The capture script of the Implementation, run as `npm run screens:capture` where the Implementation's code is kept, plays one fixed scenario and writes the images to `docs/images/screens`. A Screenshot is never edited by hand. When a Screenshot and the Implementation differ, the Implementation is right.

A Screenshot may lag the game by up to 72 hours, so a change to how a screen looks does not by itself generate the Screenshots again. Under each Screenshot its specification states when it was captured, e.g. "Captured on 2026-11-23 19:47 UTC.". The Screenshots are generated again only when a change touches a screen whose Screenshot was captured more than 72 hours earlier, and then only the images whose content differs are replaced, each with its new capture time, which the capture script writes.

The values a Screenshot shows, e.g. the names of Agents and the numbers, are those of the capture scenario and decide nothing.

What a screen shows, in which order, and which operations it offers is stated by the [Graphical User Interface](gui.md) and by the specification of that screen or panel. How one screen arranges and sizes what it shows is decided by the Implementation and shown by the Screenshot. What several screens share, i.e. the Design tokens and the styling of components, is stated here.

# Reference window

The game is played in a browser window on a laptop, so every screen is designed for one window size and proven in it. The Reference window is 1408 px wide and 784 px tall. In it no screen scrolls sideways, and no heading, label, or button wraps onto a second line; a region that holds a list or a long text may scroll down. The Screenshots are captured in it. A larger window shows more of what scrolls, unless the [Screen limit](#screen-limit) is on, and a smaller one is not played: the [Window check](#window-check) stops play until the window is large enough.

## Window check

A screen drawn in a window smaller than the Reference window cuts off or overlaps what the Player decides by, so the GUI refuses to be played in one and shows the Player how to fix it. Sizes are in CSS pixels, so zooming the browser out makes the window hold more of them.

- **When:** On every screen, the GUI measures the viewport, the part of the browser window the page is drawn in, when it opens and whenever the window or the zoom changes. While the viewport is narrower or shorter than the Reference window, the Window check dialog stands over the screen.
- **Blocking:** While the Window check dialog stands, every button, input, and keyboard shortcut of the screen beneath it is disabled, not only covered, so that nothing can be done on it even if the dialog is removed from the page by other means, e.g. the browser's developer tools.
- **Dialog:** It covers most of the window, over a Scrim, with a 2 px Warning top edge, has no close control, and is titled "Window too small". It states the viewport's size, the Reference window's size, and how many px the viewport lacks in each direction, e.g. "The window shows 1,280 × 700 px; the game needs at least 1,408 × 784 px. Make it 128 px wider and 84 px taller."
- **Picture:** Below the text a drawing to one scale, in CSS pixels at the browser's zoom, shows the screen the window is on, the viewport within it, placed where it stands on that screen when the browser reports the window's position and centred otherwise, and the Reference window as a dashed outline over the viewport. A browser reports a window's position from the corner of the main screen, so a window on another screen, e.g. one to the left of the main screen, is placed from the corner of its own screen. Where the viewport is too narrow, the outline grows from it toward the side of the screen with room for it, to the right unless only the left has room, and an arrow in Accent that pulses points that way from that edge; where it is too short, likewise down unless only the top has room.
- **Screen too small:** When the available screen, less the browser's own frame around the viewport, is narrower or shorter than the Reference window, resizing the window cannot help. The dialog then says so, and suggests zooming out, e.g. with Ctrl and minus, or moving the window to a larger screen.
- **Large enough:** Once the viewport is large enough, the dialog stays and turns to success: its top edge and title turn Positive bright, the title reads "Window large enough" with a check mark before it, the arrows go, and a primary Continue button dismisses it, enabling the screen again. When the window shrinks below the Reference window again, the dialog stands again.

## Screen limit

A Player whose window is larger than the Reference window, e.g. the Game designer at a wide monitor, can still play the game exactly as the Reference window shows it. The Screen limit is a [Global configuration](../foundation/configuration.md#global-configuration) setting, set by the "Limit the screen to 1408 × 784" checkbox of the [Settings panel](gui.md#settings-panel).

| Setting      | Permitted values | Game build default |
| ------------ | ---------------- | ------------------ |
| Screen limit | On or off        | Off                |

While the Screen limit is on, every screen, with everything shown over it, e.g. a [dialog](#dialogs), is drawn in an area as wide and as tall as the Reference window, centred in the window. The rest of the window is an Out of bounds fill, a shade darker than the Background, so that the Game designer sees where the area ends, e.g. to check that a screen fits the Reference window; no line or frame marks the edge. In a direction in which the window is smaller than the Reference window, the area is as large as the window. While the Screen limit is off, a screen fills the window.

## Danger scale

Wherever a colour runs smoothly from neutral to red as a value grows worse, it follows the Danger scale, so that a shade means the same severity on every screen. Each use states its severity, from 0%, nothing wrong, to 100%, the worst, e.g. the share of a limit reached. The stops are Text at 0%, Warning at 25%, Accent text at 50%, Danger at 75%, and Danger deep at 100%; a severity between two stops takes the colour between them in proportion, mixed in sRGB, e.g. 12.5% is halfway between Text and Warning.

## Typography

Three typefaces separate three kinds of text: condensed headings name things, the body font explains them, and the monospaced font carries every number and identifier. All three are Google Fonts.

| Section heading | Barlow Condensed | 700 | 22 px | Uppercase, 0.08 em | The heading of a Main menu column, the title of a dialog, and the title of a Detail view. |
| Panel heading | Barlow Condensed | 700 | 18 px | Uppercase, 0.08 em | The heading of a panel, a table, or a headline chart. |

| Button | Barlow Condensed | 600 | 14 px | Uppercase, 0.1 em | Button text; 17 px on a screen's main action. |

Every style in Barlow or Barlow Condensed therefore widens each space by 0.1 em of word spacing, whatever its size or its letter spacing, so that a space always reads as one. | Headline figure | JetBrains Mono | 400 | 22 px | Tabular figures | A status bar value and the current value of a chart. | | Axis | JetBrains Mono | 400 | 11 px | Axis colour | Chart axis labels. |

Text steps down as it nests, so that the Player reads how a screen is built before reading its words: text nested under a heading is never larger than that heading, and each further level is no larger and no brighter than the level it sits under. E.g., in the Turn Summary, the "New Mission sites" Group heading outranks the name of each new Mission site under it, in Body and Text, and the name outranks its details, in Body and Text secondary or Text muted. A Label names a control or a column, e.g. "Assign to" before the Assignment buttons of the Agents View or a table header, and never heads a group of items.

## Spacing and shape

Even spacing is what makes the screens read as orderly, so spacing follows fixed steps rather than case-by-case values.

- Controls in one group, e.g. Load and Delete, are 8 px apart.
- Panels stacked in one column are 16 px apart on the Campaign screen and 24 px apart on the Main menu; columns are 24 px apart on the Main menu. The regions of the Campaign screen meet without a gap.
- A panel has 18 px of inner padding; a table cell has 8 px vertical and 10 px horizontal padding.
- The Main menu has at least 24 px of outer padding, and the Main menu content is at most 1216 px wide and centred.
- Controls have a 2 px corner radius; panels and cards have square corners and no outline.
- Two pieces of text on one line never touch: they are at least 8 px apart, or joined by a " · " separator, e.g. a Mission site's name, kind, and Faction, and a value right-aligned after them.

## Alignment

A screen reads as one instrument only when its parts line up, so every element is aligned with its neighbours by these rules, at every window width, and no alignment is left to the content an element happens to hold.

- **Text on one line:** pieces of text of one size on one line share one baseline. Smaller text after a heading on its line, e.g. the free places and their cap bars after the title "Agents" in the Agents View or the money after the title of the Upgrades View, is centred on the heading: the middle of its capitals sits level with the middle of the heading's capitals, never on the heading's baseline. Text is never centred on its line by the height of its box, because styles of different sizes then sit at different heights.
- **Controls in one row:** the controls of one row, e.g. the filters, buttons, and close control of a Detail view's title row, are equally tall and share one centre line. Text in the row, e.g. a count of selected rows after a button, is centred on that line too.
- **Labelled groups:** a group of controls with a Label, e.g. the Assign to buttons of the Agents View, has its Label before its controls on their line, centred on the row's centre line, never above them, because a Label above its controls makes its row a line taller and takes that line from the table below.
- **Cards side by side:** cards in one row are equally tall, and each part of a card starts at the same height on every card of the row, because each part takes the height of its tallest instance in the row. E.g., when the change of one Upgrade card wraps onto a second line, the Buy buttons of all the Upgrade cards still sit on one line.
- **A note beside a control:** a note about a control, e.g. the money missing for a disabled Buy button, sits on the control's row, 8 px after it, and never moves below it; a note longer than the space left beside the control wraps within that space. The note never sets the row's height: the row is as tall as its controls, and a wrapped note stays centred on their centre line and extends above and below it into the spacing around the row.
- **Controls stay still:** a control keeps its place and its size whatever changes around it, e.g. a button turning disabled, a note that appears or wraps, or a count that grows, so that the Player's hand finds it where it was a moment ago. Content that changes grows away from the controls, e.g. downward below them, or within space reserved for it.

# Components

Components are the building blocks every screen reuses. A screen that needs a control not described here builds it from the Design tokens in the same manner.

## Buttons

Buttons come in five kinds so that the Player can tell at a glance what a button will do.

- A neutral button has a Raised fill, a Border outline, and Text-coloured text.
- A primary button has an Accent fill and On-accent text. A panel has at most one primary button, and it is the action the panel exists for, e.g. Start a new Campaign or Advance turn.
- A destructive button has no fill, a Danger border outline, and Danger text, e.g. Delete and Delete campaign.
- A weighty button has no fill, a Warning outline, and Warning text. It marks a reversible step with a larger reach than its usual form, e.g. Undo Turn in place of Undo Action.
- An Autopilot button has no fill, an Autopilot outline, and Autopilot text. It marks a reversible step that crosses an [Autopilot engagement](../foundation/engine-contract.md#autopilot), e.g. Undo Autopilot in place of Undo Turn, so that it never passes for a step of the Player's own play.

A button is 36 px tall, 32 px inside a table row, and 44 to 46 px for the main action of a screen. A button's label never wraps onto a second line. Buttons that belong together sit in one row. A row of buttons that follows content on the same line, e.g. the Load and Delete of a Campaign save, or that ends a panel or dialog, aligns to the right edge of its row or panel. A row of buttons that is a part of its own in a card whose parts are stacked, e.g. the Buy button of an Upgrade card, starts at the card's left content edge, as the card's text does. When a row is too narrow, the whole group wraps below the content, never a single label. A disabled button keeps its kind and is drawn at 60% opacity, so that its label stays readable over a [Background artwork](#background-artwork).

The Player learns a keyboard shortcut from the control it presses, so the tooltip of every button, checkbox, or tab that a key presses names that key, whether the control is enabled or disabled, e.g. "Next article · Shortcut: W" or "Close · Shortcut: Esc". The Escape key is named only on the control it presses at that moment, e.g. on the Back control and not on the close control while a Back control is shown.

## Inputs

Inputs share one shape so that every editable value is recognisable. An input or a select is 40 px tall, has a Background fill, a Border outline, and Body text. Its label sits above it in the Label style, or to its left with a muted hint below the label when the input is one row of a settings list. A numeric input uses the Figure style and aligns its value to the right.

## Steppers

A stepper sets a count: a numeric input between a "−" and a "+" button, 24 px tall. Clicking a button changes the count by 1, by 10 while Shift is held, and by 100 while [Ctrl](gui.md#glossary) is held, and never past the stepper's bounds, so that large counts take a few clicks rather than many.

## Checkboxes

A checkbox shows at a glance whether the Player can change it, because a disabled checkbox among enabled ones, e.g. the row of an Agent In transit in the [Agents View](screens/agents-view.md), must not pass for one the Player can select. A checkbox is a 16 px square with the control corner radius, drawn in these states.

- **Enabled, unchecked:** a Background fill and a 1 px Text muted outline.
- **Enabled, checked:** an Accent fill and outline, with an On-accent tick.
- **Disabled, unchecked:** no fill and a 1 px Divider outline, so it reads as an empty slot.
- **Disabled, checked:** an Accent dim fill and outline, with a Text muted tick.

The pointer over a disabled checkbox shows that it cannot be changed. A checkbox's label, when it has one, sits to its right in Body text, 8 px from it.

## Sliders

A slider shows its value as the filled share of its track, so the Player reads it at a glance, e.g. the [Music volume slider](music.md#music-volume-slider). The track is 4 px tall with fully rounded ends, in Accent from its left end up to the thumb and in Divider beyond. The thumb is a 14 px Accent circle whose centre sits at the end of the filled part, so that the track spans exactly the thumb's travel: no part of the track is filled at the least value, all of it is at the greatest, and the thumb overhangs either end by half its width.

## Panels and cards

A panel groups what belongs together on a Surface fill. A card is a panel for one item of a list, e.g. one Campaign on the Main menu; it has a 2 px top edge in Border, or in Accent when it is the item the Player most likely wants, e.g. the Campaign of the most recent [Campaign save](../foundation/engine-contract.md#persisted-data).

A panel that lists groups, e.g. the panel of the Campaign screen that lists the work waiting for the Player, heads each group with a Group heading and its count in the Figure style and Accent text, and separates groups with Divider rules. In a panel whose items take one line each, each item is a row at least 28 px tall, separated by Raised dividers: its name in Body on the left, and its value, e.g. a [Completion estimate](gui.md#glossary), right-aligned in the Figure style and Text secondary, with a [Progress circle](gui.md#glossary) between them. A name that wraps onto a second line makes its row taller, and its value and [Progress circle](gui.md#glossary) stay centred on the row. In a panel whose items take more than one line, an item's value, e.g. the [Turns](../foundation/engine-contract.md#player-actions-and-turns) until expiration of a new [Mission site](../mechanics/domain-model.md#leads-investigations-mission-sites-and-missions), is likewise right-aligned on the item's first line, in the Figure style when it is a number, and the item's further lines hold its details. The item's name is in Body and Text, and its details are in Body or Figure and in Text secondary or Text muted, unless a colour of a state applies.

A [Completion estimate](gui.md#glossary) whose earliest Advance turn is the next one is in Accent text, and "in transit", "stalled", and "ETA ?" are in Text muted. In the [Turn summary](screens/turn-summary.md#glossary), a new Mission site that expires within two [Turns](../foundation/engine-contract.md#player-actions-and-turns) shows its Turns until expiration in Accent text, and in the [Missions View](screens/missions-view.md#mission-site-list) the details of such an Active Mission site, its Turns until expiration included, are in Accent text.

## Dialogs

A dialog interrupts the screen only for what the Player must see before going on, e.g. what an Advance turn did. It sits centred over a Scrim on a Surface fill with a 2 px Accent top edge, at most 640 px wide, with its title in the Section heading style and its [buttons](#buttons) in one row at the bottom right; the action that dismisses it is primary. The [Turn summary](screens/turn-summary.md#layout) is the exception: it is wider, for its [Event art](screens/turn-summary.md#glossary), and its control row holds buttons on the left and in the centre as well. A dialog taller than the window scrolls inside, keeping its title and buttons in view.

## Close controls

The Player closes every view opened over a screen the same way and finds its close control in the same place, so that closing never needs a search. The views that close this way are a [Detail view](gui.md#glossary), the [Settings panel](gui.md#settings-panel), the keyboard shortcuts, the developer tools, and the [Main menu](screens/main-menu.md) reached from the Campaign screen. A dialog that ends with buttons, e.g. the [Turn Summary](screens/turn-summary.md), is closed by those buttons instead.

- **Shape:** the close control is a square neutral button, 36 px wide and tall, holding a ✕, never a text button, e.g. one labelled Close.
- **Place:** it ends the title row of its view, at the right edge of the view's rectangle inset by that view's inner padding, never at the corner of the window when the view is narrower. It sits on the title's line, centred on it, whatever else the row holds, so that the ✕ is at the same place in every Detail view.
- **Escape:** the Escape key does what the close control of the topmost open view does, except in a Detail view that shows a [Back control](gui.md#glossary), where it [does what the Back control does](screens/campaign-screen.md#view-trail), and except while the [search field of the Compendium View](screens/compendium-view.md#panes) holds text, where it clears that field.

## Tables

Tables carry most of the game's data, so they are dense but aligned.

A header row uses the Label style over a Border rule; body rows are separated by Raised dividers. Columns that hold numbers use the Figure style and are right-aligned, their header included. Row actions are [buttons](#buttons) in the last column. Text that encodes a state uses the colour of that state, e.g. Positive for a won Mission, and Text muted for an idle Agent.

A table keeps its columns still, so that the Player's eye finds a value where it was a moment ago: each column has a fixed width set by the table's design, and neither what the rows hold nor the width of the screen changes it, e.g. an Assignment that gains the [In transit icon](#icons) or a filter that hides rows moves and resizes no column. The columns sit side by side from the table's left edge and none stretches, so that every value stays close to the rest of its row and the spare width of a wide table lies to the right of its last column.

A table fits its view, because a table that scrolls sideways hides the columns the Player decides by. In the [Reference window](#reference-window) with the [Side panel](gui.md#glossary) shown, a table is no wider than the Detail view, i.e. 1068 px, or than its pane, and what does not fit is left out by rank: first come the columns that name a row and act on it, then the figures that the view's decision needs, and everything else moves one step away, e.g. into the details of the row, a tooltip, or the view whose task needs it. E.g., the [Agents View](screens/agents-view.md) leaves what its Agents wear to its Equip table, one press away. Only in a window narrower than the Reference window does a table scroll sideways within its panel.

Every row of a table is one line tall, so that rows line up and a long value does not push the rows below it down. Each column is wide enough to hold on one line every value that the specifications list for it, e.g. the Assignment "Recovery · 3 T left" in the Agents View. At most one column of a table holds free text, e.g. the message of an engine rejection or the events of a Turn; it takes the width the other columns leave, and a value too long for it is cut short with "…" and shown in full while the pointer rests on it. A header is worded to fit the values under it and never makes its column wider than they need, e.g. "Exh." over an exhaustion. A header shortened from the name of what its column shows has that name as its tooltip, wherever the column stands, e.g. "Combat rating" for "CR" and "Exhaustion" for "Exh.", so that the Player can always learn what a short header means. In every table, an [effective skill](../mechanics/agents-spec.md#combatant-attributes) is headed "Skill" and a [base skill](../mechanics/agents-spec.md#combatant-attributes) "Base", because effective skill is the one the Player decides by.

A column that shows a game quantity is wide enough for the widest value that quantity can take, in every table and whatever values the [GDRs](../foundation/core-concepts.md#game-build-and-content) give, so that a veteran [Agent](../mechanics/domain-model.md#agency-and-agents)'s row late in a long Campaign is never cut short. A value of four or more digits includes the commas of its [Digit grouping](gui.md#digit-grouping), e.g. "1,234" is five characters wide, and so does a column of any other number that can reach 1,000, e.g. money or a Turn:

| Quantity | Widest value |
| --- | --- |
| Agent, i.e. an [Agent name](../mechanics/agents-spec.md#agent-names) | 30 characters, the most an [Agent name](../mechanics/agents-spec.md#namelist) can hold, followed by the widest [Rank insignia](gui.md#glossary) where the column shows one, e.g. in the [deployment pane](screens/missions-view.md#deployment). |
| [Rank](gui.md#ranks) | The widest `abbreviation` of the [Rank](gui.md#glossary) GDRs followed by its [Rank insignia](gui.md#glossary), e.g. "Hi Cmdr" and three stars. |
| [Enemy label](gui.md#enemy-labels) | The longest the [Game build](../foundation/core-concepts.md#game-build-and-content) can give, with a two-digit number, e.g. "high-commander-12". |
| [Assignment](screens/agents-view.md#agent-table) | "[Recovery](../mechanics/agents-spec.md#assignments) · 99 T left" followed by the In transit icon. |
| Skill, base or effective | Four digits, e.g. "1,234". |
| [Combat rating](../mechanics/combat.md#combatant-condition-in-a-combat), e.g. CR | Four digits, e.g. "1,234". |
| Exhaustion | Three digits, e.g. "123". |
| Health | Three digits, followed by the max health it is out of when the column shows both, e.g. "123/123". |
| Armor | Three digits, e.g. "123". |
| Damage, e.g. a Weapon's damage or the damage a participant dealt or took in a Combat | Three digits, e.g. "123". |
| Experience gained, e.g. Mission experience | Three digits after its sign, e.g. "+123". |
| Chance, e.g. a hit chance | Two digits and one decimal before the percent sign, e.g. "99.9%". |

A column that shows a value at two moments joined by "→" holds the widest value on both sides, e.g. "1,234 → 1,234" for an effective skill, "123 → 123/123" for a health, and "123 → 123" for an armor. A column that shows several quantities in one value holds the widest value of each, e.g. "99.9% (1,234 vs 1,234)" for a hit chance with the effective skills it compares.

A table whose rows each have a selection checkbox lets the Player select several rows at once, in these ways:

- **Click:** clicking a row's checkbox, or the row outside its links and buttons, selects or clears that row and makes it the anchor.
- **Shift-click:** Shift-clicking a row gives every row from the anchor to that row, both included, the state the anchor has. E.g., in a table of ten Agents, after clicking the tenth to select it and then Shift-clicking the third, the third to the tenth are all selected.
- **Drag:** pressing on a row and moving the pointer across others gives each row passed over the state the pressed row took, so one drag selects or clears a run of rows.

A row whose checkbox is disabled is skipped by every one of these. Pressing or dragging over the rows never selects their text.

The header row holds a Select all checkbox above the rows' checkboxes. Checking it selects every shown row whose checkbox is enabled, and it stays checked while the selection follows that set: whenever which rows are shown, or which of them can be selected, changes, e.g. because a filter changed, the selection becomes exactly the shown rows that can be selected. Unchecking it clears the selection, and clicking, Shift-clicking, or dragging over any row unchecks it and keeps the selection as it then is.

A table whose column headers sort it remembers up to four sort tiers, so that a new sort refines the earlier ones instead of discarding them. Rows are ordered by the first tier, rows equal in it by the second, and so on, and rows equal in every tier keep the table's default order. Pressing a header works as follows:

- **A column in no tier** becomes the first tier, descending when it holds numbers and ascending otherwise; every earlier tier moves down one, and a tier pushed past the fourth is dropped.
- **The column of the first tier** flips its direction.
- **The column of a lower tier** becomes the first tier with the direction it had, leaving its old tier, and the tiers that were above it move down one.

E.g., after sorting the [Agent table](screens/agents-view.md#agent-table) by effective skill and then by Assignment, the rows are ordered by Assignment, and the rows of one Assignment by effective skill.

A view may lock a tier above the four, which need not be a column, e.g. the Agent table puts the Agents that can be selected first while an [Assignment filter](screens/agents-view.md#glossary) is on. Pressing the header of a locked tier that is a column changes nothing, and pressing any other header changes the tiers under it as above.

Only the header of the column of the first tier shows its direction, as ▲ for ascending or ▼ for descending, after its label, in the header's own colour, so that the table names one sort and stays quiet. The first tier is the first column tier, so a locked tier that is no column passes the arrow to the tier under it. The lower tiers still order the rows but show no arrow. A header is never cut short: each column's width holds its header's label together with that arrow.

A table whose rows stand in groups, each under a group row, e.g. the Weapons, Armor, and Ammo of the [Storage View](screens/storage-view.md), lets the Player fold each group, so that a long group does not push the others out of view. Pressing a group row anywhere folds its group, hiding the group's rows, and pressing it again unfolds it. The group row starts with ▾ while its group is unfolded and with ▸ while it is folded, and it keeps what else it shows, e.g. its sums, either way. Every group is unfolded whenever its view opens.

## Agent condition

Wherever a table shows an [Agent](../mechanics/domain-model.md#agency-and-agents)'s [exhaustion](../mechanics/agents-spec.md#combatant-attributes) or [current health](../mechanics/agents-spec.md#combatant-attributes), its colour tells the Player at a glance how worn down the Agent is, so that a tired or hurt Agent stands out before it is sent anywhere. The outcome of an attack in a Combat log is the one exception: its colour says [whom the attack favours](screens/turn-report-view.md#combat-log-colours).

- **Exhaustion:** Text up to [`exhaustion_work_start_max`](../mechanics/agents-spec.md#agentparameters); Warning above it; Accent text from the midpoint of `exhaustion_work_start_max` and `exhaustion_work_limit`, rounded up; and Danger from `exhaustion_work_limit`, with a warning-triangle icon before the value. E.g., with thresholds of 25 and 60, exhaustion 25 is in Text, 26 in Warning, 43 in Accent text, and 60 in Danger with the triangle.
- **Current health:** the [Danger scale](#danger-scale), with the share of [effective max health](../mechanics/agents-spec.md#combatant-attributes) that current health falls short of as its severity. E.g., 30 of 30 is in Text, 15 of 30 in Accent text, and 1 of 30 almost in Danger deep. The share is taken from the exact current health, e.g. 29.40 of 30 is 98%.

## Icons

An icon stands for a state, alone wherever words would widen a column and after the words where the room is spare, and the pointer resting on it shows its name.

- **In transit icon:** a flying airplane, "✈", in the colour of the text it follows, marking an Agent [In transit](../mechanics/domain-model.md#agency-and-agents). In an [Assignment](../mechanics/domain-model.md#agency-and-agents) column it follows the [Assignment](../mechanics/domain-model.md#agency-and-agents) without the words "In transit".

## Consequences

Wherever a screen lists the [Consequences](../mechanics/missions.md#consequences) that applied, e.g. in a Mission of the [Turn summary](screens/turn-summary.md#summary-events), each Consequence is coloured by whether it is good or bad for the Player, so that a costly outcome stands out among the gains. A Consequence that gains money or funding, reduces [Panic](../mechanics/domain-model.md#campaign-standing), or makes a [Faction](../mechanics/domain-model.md#factions) [Eliminated](../mechanics/domain-model.md#factions) is in Positive; one that loses funding or increases Panic is in Danger. The label before them and the separators between them stay in Text muted, e.g. in "Consequences: Panic +3, funding −2" only "Panic +3" and "funding −2" are in Danger.

## Detail views and navigation

The [Side panel](gui.md#glossary) is the console beside the globe, so it reads as one dark column and the globe as open space.

- **[Globe stage](gui.md#glossary):** a Background fill behind the globe, with no panel or outline around it.
- **Side panel:** 272 px wide, whatever the width of the window, so that a Detail view gets the width a wide table needs, on a Surface fill with a 1 px Divider rule along its left edge. Its sections are separated by Divider rules and have 16 px of inner padding.
- **Navigation groups:** the groups of the [navigation](screens/campaign-screen.md#navigation) stand one under another, each its name in the Label style over its buttons.
- **Navigation buttons:** the buttons of a group sit two to a row with 8 px between them. A navigation button is a neutral button in the Button style, its name on the left and its count, if any, on the right in the Figure style and Accent text. The button of the open [Detail view](gui.md#glossary) has a 2 px Accent line along its bottom edge.
- **Detail view:** it covers the whole Globe stage, edge to edge with no margin around it, on a Surface fill with 18 px of inner padding. It has no top edge of its own, since the status bar's Accent bottom edge already runs along its top. Its title is in the Section heading style on the left and sits at the same place in every Detail view, starting at the top of the inner padding, so that switching Detail views never moves it. Its [buttons](#buttons) are in one row on the right, ending 8 px before the [close control](#close-controls) that ends the row. A Detail view taller than the Globe stage scrolls inside, keeping its title row in view. The [Compendium View](screens/compendium-view.md) and the [Storage View](screens/storage-view.md), which [cover the whole screen](screens/campaign-screen.md#hiding-the-side-panel), fill the whole window, with no Accent line across its top, and so does the [Combat replay](screens/combat-replay.md#whole-screen).
- **Back control:** a [Back control](gui.md#glossary) is a neutral button in the Button style, e.g. "‹ Turn report", and the last button of the row, on the title's line as the close control is, so that the Player finds it beside the ✕ in every Detail view, except where it [stands in the place of a button of the same name](screens/turn-report-view.md#turn-summary-button).
- **Rows of controls:** controls that do not fit the title's row take rows of their own under it, each one line of controls tall, e.g. the checkboxes and then the buttons of the Agents View, so that the content below keeps as much of the height as it can.
- **Panes:** in a Detail view whose content is panes side by side, e.g. the Missions View, every heading inside a pane, e.g. the name of the selected item, is in the Group heading style, so that the panes read alike and one level below the title. Each pane scrolls down on its own and the Detail view as a whole does not, so that scrolling a long list, e.g. the Concluded Mission sites, never scrolls the selected item out of view. A pane that holds a table is never narrower than that table's columns while the Detail view has room for it, and the panes share the rest of the width, so that a table scrolls sideways only when the window is too narrow for every pane to take its least width.

## Background artwork

Background artwork lets the Player enjoy a picture of the agency at work while reading a Detail view, without the picture ever competing with what the Player reads: it is drawn so faintly that it reads as part of the dark field, not as an image laid over it. It is decoration only: it shows no game state and the Player cannot act on it.

Which Detail view shows which image, and how faintly, is content rather than design, so it comes from the BackgroundArtwork [GDRs](../foundation/core-concepts.md#game-build-and-content), which serve the Display content purpose. A Detail view that no BackgroundArtwork [GDR](../foundation/core-concepts.md#game-build-and-content) names shows no Background artwork.

| Property | Meaning |
| --- | --- |
| `detail_view` | The Detail view that shows the image, by its name in lowercase words joined by underscores, e.g. `missions` for the [Missions View](screens/missions-view.md). No two GDRs name one Detail view. |
| `image` | The path of the image file, in the `assets/images/` directory, relative to the repository root, e.g. `assets/images/agents-at-work.png`. |
| `opacity_pct` | The opacity at which the image is drawn, a whole number from 0 to 100. The Content designer chooses it so that Text muted keeps a contrast ratio of at least 4.5:1 against nearly all of what lies behind it, giving up that ratio only over the image's brightest highlights. |

A Detail view draws its Background artwork at the `opacity_pct` of its GDR, whatever the Detail view holds, e.g. the Agents View showing its Memorial:

- **Place:** between its Surface fill and its content, filling the whole Detail view. The image is scaled to cover that area with its proportions kept, centred, and cropped where the proportions differ. It stays in place while the content scrolls over it.
- **Panels inside it:** a panel inside the Detail view, e.g. a pane of the Missions View, draws its Background fill at 35% opacity, so that the image shows through it too while the panel still reads as an area of its own. A selected row and a button keep their fills opaque.

When the image cannot be loaded, the Detail view looks as it would without it.

### Artwork tuning

Artwork tuning lets the Game designer settle each image and its opacity while seeing them in the game, before writing the chosen values into the BackgroundArtwork GDRs. The developer tools, opened from the [Settings panel](gui.md#settings-panel) of the Campaign screen, hold an Artwork tuning section, which stacks these controls in this order, each under its Label in the manner of [Inputs](#inputs), 16 px apart:

- **Detail view:** a select of the Detail views that a BackgroundArtwork GDR names, each shown by its name, e.g. "Missions", starting at the Detail view of the first GDR. The controls below it tune the Background artwork of the picked Detail view alone, and picking another Detail view keeps the values already tuned for each.
- **Opacity:** a slider from 0% to 100% in steps of 1%, with its value as a figure beside it, e.g. "30%". It starts at the `opacity_pct` of the GDR.
- **Image:** a select of every image file in the `assets/images/` directory, each shown by its file name, starting at the `image` of the GDR. Any image can be tried on any Detail view, e.g. the Agents View's image on the Missions View.

A Detail view showing that Background artwork follows a change at once, so the Game designer can keep it open while moving the slider. A Reset button ends the section, below the controls, and returns every Detail view, not only the picked one, to the values of its GDR. Tuned values are part of the [Global configuration](../foundation/configuration.md#global-configuration) setting Artwork tuning, not of [Campaign state](../foundation/core-concepts.md#campaign-and-session): it holds the tuned values of each Detail view, none by default, and the Reset button resets it, so tuned values stay in every later [Session](../foundation/core-concepts.md#campaign-and-session) until reset. Like every control of the [developer tools](gui.md#developer-tools), Artwork tuning is available only while [Dev mode](../foundation/engine-contract.md#principals-and-access) is enabled.

## Status bar

The status bar keeps the agency's vital values in view on the Campaign screen, except while the Compendium View or the Combat replay covers it. It spans the screen on a Surface fill with a 2 px Accent bottom edge. Each value sits under its label in the Headline figure style; a change of a value, e.g. projected income, follows it in a 13 px Figure style in Positive or Danger. A value with a gain and a loss, i.e. Money with its projected income and projected upkeep, stacks them in one column after it, the gain above the loss, so that they widen the status bar only once. The screen's controls follow the values, with the main action, e.g. Advance turn, last and primary. The values and the controls share one row in the [Reference window](#reference-window) and every wider one, and none wraps onto a second line, because a second row takes its height from every Detail view; a label is therefore short, and a unit follows its value in the 13 px Figure style and Text muted, e.g. the "T" of Enemy quiet.

## Meters

A meter shows a value against its limit, e.g. Panic against the Panic limit. It is a row of 10 equal segments, 8 px tall with 3 px gaps. Its colour says how near the limit the value is, on the [Danger scale](#danger-scale) with the share of the limit reached as its severity. Each full tenth of the limit fills one segment in that colour, a remaining part of a tenth fills the next segment in that colour at 50% opacity, and the other segments are Divider. The value and the limit are written above the meter's right end in that colour, e.g. "24.35 / 100%" almost in Warning.

## Cap bars

A cap bar shows at a glance how much of a cap is taken, e.g. of the [Agent cap](../mechanics/domain-model.md#agency-and-agents), so that the Player sees how much room is left without reading numbers. It is a solid bar 80 px wide and 8 px tall on a Divider track, whatever the size of the cap, so that a growing cap never widens it. Its fill covers, from the left, the share of the cap that is taken, coloured as the Fill of [Progress bars](#progress-bars) by that share; a cap with more taken than it allows shows a full bar. The exact values stand beside the bar as text.

## Tallies

A tally shows a count that has no limit as a stack of marks, so the Player can compare counts at a glance, e.g. the Acquisitions of each Upgrade. It is one Accent square per counted item, 12 px wide and tall with 3 px gaps, filled left to right in rows of 10, e.g. 13 items show one full row and 3 squares under it. It shows at most 10 rows, so a count above 100 still shows 100 squares. The exact count is also shown as text, e.g. "Bought 137×".

## Progress bars

A [Progress bar](gui.md#glossary) lets the Player read at a glance how close an [Investigation](../mechanics/domain-model.md#leads-investigations-mission-sites-and-missions) is to completing, so its colour warms as completion nears instead of switching hue. It is 8 px tall in a panel row and 10 px in a dialog, on a Divider track.

- **Fill:** its colour runs linearly from Accent dim at 0 to Accent at the [Required progress](../mechanics/leads-and-progression.md#glossary), by the share of the Required progress reached, and stays Accent beyond it.
- **Zone and tick:** the zone from the Required progress to the end of the bar is hatched with diagonal stripes of Raised and Border. The tick at the Required progress is a 2 px Text line that overhangs the bar by 3 px above and below. The Required progress and the greatest value of the range are written under the tick and under the bar's end in the Axis style.
- **Preview:** the preview segment of the projected progress gain is Positive at 30% opacity.
- **Caption:** a caption under the bar is in 12 px Body and Text muted, or in Accent text when it says that the Investigation may complete next turn or any turn, with the projected progress gain on its right in the Figure style and Positive, e.g. "+1.74 / turn".
- **Unscaled bar:** the bar of a [Lead](../mechanics/domain-model.md#leads-investigations-mission-sites-and-missions) that is not an [Assessed Lead](../mechanics/investigations.md#glossary) has a dashed track of Divider dashes 6 px long with 4 px gaps, and an Accent dim stub 12% of its width.
- **Completed Investigation:** in a dialog, the gain of the last Advance turn is a Positive segment labelled with that gain above it in Positive, and the point where the Investigation completed carries a check in a Positive circle 20 px wide, with the check in Background and the final [Investigation progress](../mechanics/domain-model.md#leads-investigations-mission-sites-and-missions) under it in Positive. When the final Investigation progress would overlap the Required progress or the greatest value of the range written under the bar, that value of the range is left out, and the final Investigation progress keeps its place.

## Progress circles

A [Progress circle](gui.md#glossary) is 18 px wide and sits on the text line it belongs to. Its track is a 1.5 px Border ring, and its fill is a sector from the top, clockwise, coloured as the Fill of [Progress bars](#progress-bars). A full circle is an Accent disc with a check in On accent. The circle of a [Lead](../mechanics/domain-model.md#leads-investigations-mission-sites-and-missions) that is not an [Assessed Lead](../mechanics/investigations.md#glossary) is a 1.5 px dashed Accent dim ring with a question mark in a 9 px Figure style and Text muted.

# Charts

Charts must let the Player read a trend across the whole Campaign without squinting. Every chart sits in its own panel with its title on the left of its title row, and on the right of that row its current value in the Headline figure style, then its Last 100 Turns checkbox and its Full screen button, which always end the row, so that every chart keeps them in the same place. A chart with several series shows no current value, because no one value sums it up, and has its legend on a row of its own under the title row instead.

- A chart's vertical axis starts at 0 and labels its top and bottom values; the horizontal axis labels the first and last [Turn](../foundation/engine-contract.md#player-actions-and-turns), in the Axis style. A chart whose series also fall below 0 labels its top and bottom values and draws its baseline at 0.
- Grid lines are Raised; the baseline is Border.
- A chart with one series draws it as a 2 px line in Text colour with its latest point marked by a dot. A chart with several series draws each in its [series colour](#chart-series-colours): a line series as a 2 px line with its latest point marked by a dot, and a bar series as a segment of a stacked bar. A dot is 7 px across, and every line, outline, and dot keeps its size on screen however wide the chart is drawn.
- A stacked bar stands for one Turn and is 70% as wide as one Turn's share of the plot, with no gap between its segments. Its segments are stacked in the order of the legend, outward from the baseline, and a series whose value is 0 in that Turn draws no segment.
- A line series drawn over stacked bars has a 4 px Background outline beneath its 2 px line, so that it stays apart from a bar segment of a like colour behind it, and the line, its outline, and its dot are drawn at 70% opacity, so that the bars behind them stay readable, e.g. the Net flow line of the Money flow chart.
- A legend lists the series in their order, each as a 10 px square in its colour, or a 10 px by 2 px stroke for a line series, followed by its name in the Axis style in Text secondary, starting at the left, and wraps onto further lines when the chart is too narrow for one.
- While the pointer rests on a Turn of a chart with a legend, a line below the chart reads that Turn's values in the Axis style in Text secondary: "Turn" and its number, then each series with its value in legend order, leaving out every series whose value is 0. A chart whose stacked bars all count one quantity above the baseline, e.g. Agents, starts the list with "Total" and the sum of the bar, because the total is what its legend cannot show, e.g. "Turn 94: Total 40 · [Standby](../mechanics/agents-spec.md#assignments) 8 · [Training](../mechanics/agents-spec.md#assignments) 6 · [Contracting](../mechanics/agents-spec.md#assignments) 10". The line keeps its height while the pointer rests on no Turn, so that the charts below it never move.
- A chart whose series count two kinds of quantity, e.g. money and Agents, labels the vertical axis of the first on the left and of the second on the right, and names the right-axis series in its legend after the left-axis ones.
- In the [Reference window](#reference-window), a chart's plot area is at least 120 px tall, and at most two charts sit side by side, so that the title row of each keeps one line.
- Every chart has a "Last 100 Turns" [checkbox](#checkboxes) in its title row, after its current value and before its Full screen button, so that the Player can look closely at the recent Turns of a long Campaign. While it is checked, the chart shows only the last 100 of the Turns it would otherwise show, labels the first and last of them on its horizontal axis, and scales its vertical axis to the values of those Turns. Each chart keeps its own checkbox, unchecked by default, in the [Global configuration](../foundation/configuration.md#global-configuration) setting Last 100 Turns charts, which holds the charts whose checkbox is checked, so each stays as the Player last left it in every later [Session](../foundation/core-concepts.md#campaign-and-session).
- Every chart has a Full screen button, ⤢, at the very right end of its title row, so that the Player can read the Turns of a long Campaign one by one. Pressing it shows the chart alone one step away, in place of its view's content, as a [Follow](screens/campaign-screen.md#view-trail), with its title row, legend, and Last 100 Turns checkbox, and its plot taking the rest of the height; its lines, dots, and labels keep their usual size on screen. The chart then covers the whole screen as the [Combat replay](screens/combat-replay.md#whole-screen) does, i.e. the status bar, the Side panel, and the Globe stage, and the Campaign screen takes no keyboard shortcut but Escape meanwhile; it shows no Full screen button, and the Back control and the Escape key return to its view.
